
## Project Overview

SpineIQ — a **direct-to-consumer** Android app for personal back pain
self-assessment and spine health tracking. The user assesses themselves (there
is no clinician, patient roster, or clinic operator). The app computes a Spine
Severity Score (SSS, 0–11), a three-tier Lifestyle Risk score, and a composite
Back Pain Risk classification, then produces a personalised in-app report and
exportable PDF. It is a screening / decision-support tool — it never recommends
specific treatments.

Single-user, single-profile ("Personal Health App"). Phase 1 prototype targeting
the public Google Play Store. The authoritative spec is **`PROJECT_PLAN.md`**
(repo root); code comments cite its section numbers (e.g. "Section 10.3",
"OQ-06").

## Tech Stack

- **Language/UI**: Kotlin 2.0.21, Jetpack Compose (Material 3), Navigation Compose
- **DI**: Hilt (`@HiltViewModel`, KSP)
- **Persistence**: Room + SQLCipher (encrypted at rest), `@TypeConverters` for enums
- **Async**: Kotlin Coroutines + `StateFlow`
- **PDF**: Android `android.graphics.pdf.PdfDocument` (on-device, no server)
- **Health Connect**: dependency declared, **not yet implemented** (see workflows doc)
- **Build**: Gradle KTS + version catalog (`gradle/libs.versions.toml`); JDK 11;
  minSdk 26, target/compileSdk 36

## Key Directories and Responsibilities

| Path | Responsibility |
|---|---|
| `app/src/main/.../ui/` | Compose screens + ViewModels, grouped by feature (`home`, `assessment`, `results`, `settings`) |
| `app/src/main/.../navigation/` | `Screen.kt` (routes) + `NavGraph.kt` (nav host, wizard nested graph) |
| `app/src/main/.../ui/common/` | Shared composables (`SpineIQComponents.kt`) and assessment draft state |
| `core/scoring/` | **Pure** scoring engine — SSS, lifestyle, composite risk. No Android deps. |
| `core/data/` | Room DB, entities, DAOs, repositories, Hilt `DatabaseModule` |
| `core/pdf/` | `PdfExporter` — renders the 12-section report PDF |
| `core/scoring/.../thresholds/` | Age-adjusted lifestyle thresholds (data only) |

Module graph (one-directional): `:app` → `:core:{scoring,data,pdf}`;
`:core:{data,pdf}` → `:core:scoring`. Never add a reverse dependency.

## Build / Test / Run

```bash
./gradlew :core:scoring:test        # fast pure-JVM rule tests (primary feedback loop)
./gradlew :app:assembleDebug        # build debug APK
./gradlew :app:installDebug         # install on device/emulator
./gradlew build                     # full build
./gradlew connectedDebugAndroidTest # instrumented tests (needs device)
```

On Windows use `.\gradlew.bat`. See `.claude/docs/development_workflows.md` for
task recipes (adding a scoring rule, a screen, an entity, migrations).

## Architecture Summary

- **MVVM**: each screen has a `@HiltViewModel` exposing one immutable state object
  via `StateFlow`; composables collect with `collectAsStateWithLifecycle()`.
- **Pure scoring**: `ScoringEngine.compute(AssessmentInput)` → `ScoringResult` is
  side-effect-free and the single source of scoring truth. Thresholds isolated in
  `AgeThresholds.kt` (NFR-08: change a rule without touching UI).
- **Assessment wizard**: 6 screens share one `AssessmentSessionViewModel` scoped to
  a nested nav graph; input accumulates in immutable `*Draft` objects, persisted
  per-section to Room.
- **Repository + DAO**: `@Singleton` repositories expose `suspend` writes / `Flow`
  reads; assessment sections are separate tables keyed by `assessment_id`.
- **Static report rules engine**: report narrative is generated by if-then rules
  over the stored scores — no LLM (FR-10). UI report and PDF render the same data
  through two renderers; keep them in sync.

Detail in `.claude/docs/architectural_patterns.md`.

## Important Caveats

- **Red flag override**: any positive red flag forces total SSS = 11 and
  Severe/High Risk. Never weaken this. (`domain_knowledge.md`)
- **DB migrations**: currently `fallbackToDestructiveMigration()` — schema changes
  wipe local data. Acceptable for Phase 1 only.
- **Health Connect** is unimplemented; all activity/lifestyle data is manual entry.
- **Single user only**: the data model has one `UserProfile` record per install.
  There is no patient management, patient list, or multi-user support.
- **Phase 1 scope**: no body diagrams, LLM narrative, cloud sync. Onboarding,
  push notification reminders, and progress/trend tracking ARE in Phase 1 scope.
  Confirm before adding anything else.
