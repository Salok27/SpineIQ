# SpineIQ — Personal Back Pain Self-Assessment & Spine Health Tracker

A direct-to-consumer Android app that empowers individuals to understand their own spinal health risk through a structured, evidence-based self-assessment. The user assesses themselves — there is no clinician, no patient roster, and no clinic operator. The app computes a Spine Severity Score (SSS, 0–11), a three-tier Lifestyle Risk score, and a composite Back Pain Risk classification, then produces a personalised in-app report and exportable PDF — entirely on-device, with no server dependency.

**Phase 1 · Public Google Play Store · Single-user personal health app**

---

## Features

### Personal Profile
- Single user profile set up on first launch, editable from Settings at any time
- Captures demographics: name, age, gender, height, weight
- Auto-calculated BMI and BMI category (Underweight / Normal / Overweight / Obese)
- Full assessment history with longitudinal score tracking

### Assessment Wizard (6-screen sequential flow)
- **Occupation & Work Pattern** — occupation type, sitting/standing/driving hours per day, lifting activity level
- **Lifestyle Assessment** — sleep hours, sleep quality, walking minutes, exercise frequency and type, active minutes (manual entry; Health Connect import planned)
- **Pain Assessment** — pain locations (text checklist, 6 regions), VAS intensity (0–10), duration, pattern, triggers, radiculopathy severity, radiation location, functional limitations
- **Functional Assessment (SSS Modified ODI)** — 5 activities rated Normal / Mild Difficulty / Severe Difficulty
- **Red Flag Screening** — 8 mandatory Yes/No items; immediate alert if any flag is confirmed
- **Review** — full summary of all entered data with section-level edit navigation before final submission

### Scoring Engine (Pure, Independently Tested)
- **VAS Pain Score** (0–2 pts): Mild (0–3) / Moderate (4–6) / Severe (7–10)
- **Radiculopathy Score** (0–3 pts): None / Mild / Moderate / Severe
- **Disability Score — SSS Modified ODI** (0–2 pts): 5 activities × 0–2, summed 0–10, mapped to points
- **BMI Mechanical Load Score** (0–2 pts): Normal / Overweight / Obese
- **Chronicity Score** (0–2 pts): Acute (<3 wks) / Subacute (3–6 wks) / Chronic (>6 wks)
- **Red Flag Override**: any confirmed flag forces total SSS = 11 and Severe/High Risk classification
- **Total SSS Score** (0–11) with four severity tiers (Low / Mild-Moderate / Moderate-Severe / Severe-High Risk)
- **Lifestyle Risk** (3-tier: Low / Moderate / High) across four components — sitting, walking, exercise, sleep — with age-adjusted thresholds (4 age groups) and two modifiers:
  - Sleep quality modifier (Poor/Fair shifts sleep risk tier upward; Excellent shifts it downward)
  - Exercise type modifier (high-impact/spine-loading types shift exercise risk tier upward)
- **Composite Back Pain Risk** via SSS × Lifestyle combination matrix (7 output classifications)

### Results & Reporting
- Results Dashboard with prominent SSS score, severity tier badge, lifestyle risk tile, and sub-score breakdown
- Full 12-section in-app assessment report generated by a static rules engine (no AI/LLM)
- PDF export — on-device, A4, 12 sections, named `SpineIQ_{Name}_{YYYYMMDD}.pdf`, shared via Android share sheet

### Data & Privacy
- Encrypted local database (Room + SQLCipher + Android Keystore)
- All health data stays on-device — no external transmission in Phase 1
- In-progress assessments persisted and resumable after backgrounding
- Full offline operation — no network required for any core feature

## Architecture

SpineIQ follows a strict MVVM architecture with a multi-module Gradle setup. The module dependency graph is strictly one-directional — no reverse dependencies are permitted.

```
:app  ──────────────────────────────────►  :core:scoring
  │                                              ▲
  ├──────────────────────────────────►  :core:data
  │                                              │
  └──────────────────────────────────►  :core:pdf
```

### Single-user local-first design
One `UserProfile` record per installation. There is no patient list, no patient selection, and no multi-user or clinic mode. All computation — scoring, classification, report narrative — runs on-device with no network dependency.

### MVVM Pattern
Each screen owns a `@HiltViewModel` that exposes a single immutable state object via `StateFlow`. Composables collect state with `collectAsStateWithLifecycle()`. All DB writes and scoring run in coroutines on `viewModelScope`; the UI is never blocked.

### Assessment Wizard
Six screens (`OccupationScreen` → `LifestyleScreen` → `PainScreen` → `FunctionalScreen` → `RedFlagScreen` → `ReviewScreen`) share a single `AssessmentSessionViewModel` scoped to a nested navigation graph. Input accumulates in immutable `*Draft` data classes. Each "Next" press calls a `persistXxx()` method that maps the draft to a Room entity and writes it. On `computeAndComplete()`, the VM assembles all data into `AssessmentInput`, calls `ScoringEngine.compute()`, stores the result, and marks the assessment `COMPLETED`.

### Pure Scoring Engine (`core:scoring`)
`ScoringEngine.compute(AssessmentInput): ScoringResult` is a side-effect-free, pure function with zero Android or I/O dependencies. It is the single source of scoring truth. Thresholds are isolated in `AgeThresholds.kt` — changing a scoring rule requires no UI changes (NFR-08).

### Static Report Rules Engine
The "Probable Contributors" narrative and "Key Risk Factors" sections are generated by if-then logic over the stored scores. No LLM or external service is involved (FR-10). The in-app report and PDF report render the same data through two independent renderers and must be kept in sync.

### Data Flow
```
UI Draft → persistXxx() → Room Entity → DAO → Repository
                                                    │
                                                    ▼
                                          ScoringEngine.compute()
                                                    │
                                                    ▼
                                          ScoresRecordEntity (stored)
                                                    │
                                          ┌─────────┴──────────┐
                                          ▼                     ▼
                                   ResultsScreen           PdfExporter
```

## Setup Instructions

### Prerequisites
- Android Studio Hedgehog or later
- JDK 11
- Android SDK with API 26–36 installed
- A physical device or emulator running Android 8.0+ (API 26+)

### Clone & Build

```bash
git clone <repository-url>
cd back_pain_prototype
```

**On macOS/Linux:**
```bash
./gradlew :app:assembleDebug
```

**On Windows:**
```powershell
.\gradlew.bat :app:assembleDebug
```

### Install on Device/Emulator

```bash
# macOS/Linux
./gradlew :app:installDebug

# Windows
.\gradlew.bat :app:installDebug
```

### Run Scoring Unit Tests (Fast — Pure JVM)

```bash
# macOS/Linux
./gradlew :core:scoring:test

# Windows
.\gradlew.bat :core:scoring:test
```

The scoring module has no Android dependency — tests run in milliseconds and are the primary fast-feedback loop for rule changes.

### Run Instrumented Tests (Requires Connected Device)

```bash
./gradlew connectedDebugAndroidTest
```

### Full Build

```bash
./gradlew build
```

> **Note:** The first build downloads all Gradle dependencies and may take several minutes. Subsequent builds are incremental.

## Development Notes

### Critical Rules — Do Not Break

- **Red flag override is absolute.** Any confirmed red flag forces SSS = 11 and Severe/High Risk classification. This logic must never be weakened or bypassed. See `domain_knowledge.md`.
- **Module dependency is one-directional.** Never add a dependency from `:core:scoring` or `:core:data` back to `:app`. See the module graph in the Architecture section.
- **Scoring engine has no Android dependencies.** Keep `ScoringEngine`, `SssScorer`, `LifestyleScorer`, and all `model/` classes free of Android imports. This enables pure JVM unit testing.
- **Two renderers, one data source.** The in-app `FullReportScreen` and `PdfExporter` must render identical information. When a report section changes, update both.
- **Single user only.** There is no patient list, no patient creation flow, and no multi-user support. Do not add any of these without confirming a scope change.

### Architectural Conventions

- Each screen has exactly one `@HiltViewModel`. State is a single immutable data class exposed via `StateFlow`. Mutations use `_state.update { it.copy(...) }`.
- Assessment wizard screens share `AssessmentSessionViewModel` scoped to the nested nav graph — do not create per-screen VMs for wizard steps.
- Changing a scoring threshold (e.g., sitting hour cutoffs) requires only editing `AgeThresholds.kt` — no UI changes needed (NFR-08).
- Enums stored in Room use `@TypeConverters`. Sets/Lists of enums are serialised as delimited strings via `Converters.kt`.

### Health Connect
The `androidx.health.connect:connect-client` dependency is declared but **no integration code exists yet**. All lifestyle data is currently `DataSource.MANUAL`. The `LifestyleDataEntity` schema already includes Health Connect fields (steps, active minutes, sedentary time, heart rate with source tracking) so no schema migration will be needed when the integration is implemented.

### Database Migrations
Schema version is currently `1`. The database uses `fallbackToDestructiveMigration()` — any schema change wipes all local data. This is acceptable for Phase 1 prototyping. Before any production release, proper `Migration` objects must be authored for every schema version increment.

### PDF Generation
`PdfExporter` uses the Android platform's `android.graphics.pdf.PdfDocument` with canvas-based drawing. There is no third-party PDF library. All drawing is manual (text, lines, page breaks). The output file is written to the app's cache directory and shared via `Intent.ACTION_SEND`.

### Distribution
Phase 1 targets the public Google Play Store. A production keystore, ProGuard configuration, Play Store listing assets, and a privacy policy are required before submission. See `.claude/docs/development_workflows.md` for the pre-release checklist.
